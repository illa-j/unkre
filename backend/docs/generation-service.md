# GenerationService

Користувацькі HTTP-маршрути: [Generations API](generations-api.md).

`domain.services.generation.GenerationService` використовує доменні сутності
та інтерфейси репозиторіїв і RunPod. У сервісі немає імпортів адаптерів,
SQLAlchemy, commit або rollback. Репозиторії працюють у наявному `session_scope()`.

Для внутрішнього CRUD доступні:

- `create(generation)` — створити запис;
- `get(generation_id)` — отримати запис або `GenerationNotFoundError`;
- `get_all(limit=100, offset=0)` — отримати сторінку записів;
- `update(generation_id, values)` — змінити поля;
- `delete(generation_id)` — видалити запис, повертає `bool`.

Методи для користувача:

- `create_generation(user_id, *, workflow_id, prompt, images=(), loras_strength=None, seed=None)`;
- `get_user_generation(user_id, generation_id)`;
- `get_user_generations(user_id, *, limit=100, offset=0)`;
- `delete_user_generation(user_id, generation_id)`.

Користувацькі методи перевіряють існування та блокування користувача. Перегляд
і видалення обмежені власником; чужа генерація повертає той самий
`GenerationNotFoundError`, що й відсутня. Список повертається від нових записів
до старих; `limit` від 1 до 100, `offset` від 0.

`create_generation()` одразу запускає RunPod. Сервіс перевіряє workflow,
належність LoRA, prompt, seed і зображення. `images` містить base64-рядки,
`loras_strength` — UUID LoRA та числові ваги. До RunPod передаються назва
workflow та імена LoRA. Якщо seed не заданий, генерується випадковий
у межах `0..2**63-1` і зберігається в записі.

Після успішного запуску зберігаються `runpod_job_id`, `runpod_endpoint_id` та
статус `QUEUED`. Наявний `recover_generations` worker бачить запис після
commit і підхоплює polling при наступному проході (щохвилини). Сервіс не
повторює запит створення RunPod автоматично. Якщо збереження отриманого
job ID завершується помилкою, сервіс пробує скасувати задачу й передає
початкову помилку виклику.

Перед перевіркою платоспроможності сервіс блокує гаманець і перечитує баланс.
Це дозволяє паралельним генераціям послідовно списувати кредити без відмови
через застарілий знімок балансу. HTTP-маршрут виконує commit перед відповіддю
201, поки клієнт RunPod ще відкритий. Якщо commit падає після прийняття job,
маршрут пробує скасувати його на збереженому endpoint і передає початкову
помилку; транзакція БД відкочується зовнішнім `session_scope()`.

Ця компенсація не гарантує скасування при аварійному завершенні процесу,
невідомому результаті мережевого timeout або недоступності RunPod. Для повної
стійкості до таких збоїв потрібний окремий механізм надійного збереження наміру
відправлення та звірки зовнішніх завдань.

Видалення активної генерації спочатку скасовує її задачу на збереженому
endpoint. При помилці скасування або активному статусі запис залишається в БД.
Завершені та ще не відправлені записи видаляються без звернення до RunPod.
Пов'язані фінансові транзакції зберігаються; їхній `generation_id` стає `NULL`.

Поля `id`, `user_id`, `created_at` не змінюються через `update()`. Вхідні
параметри вже відправленої генерації також не змінюються. Для користувацького
API використовуйте методи з перевіркою власника; загальний CRUD не перевіряє
роль виклику.
