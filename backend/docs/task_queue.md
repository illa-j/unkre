# Черга завдань

Черга використовує ARQ і Redis. Налаштування знаходяться в
`TaskQueueSettings`; значення для `.env` наведені в `.env.example`.
`REDIS_URL` та `TASK_QUEUE_NAME` мають збігатися у процесі, який ставить задачі,
і у worker.

Запуск із директорії `backend` після запуску Redis і PostgreSQL:

```sh
PYTHONPATH=src uv run arq adapters.task_queue.worker.WorkerSettings
```

Постановка задачі після збереження `runpod_job_id` та `runpod_endpoint_id`
і завершення транзакції БД:

```python
from adapters.task_queue import create_queue

queue = await create_queue()
await queue.enqueue("poll_generation", str(generation.id))
```

`create_queue()` відкриває спільний пул при першому виклику. `close_queue()`
закриває його при завершенні процесу, який ставить задачі. Worker використовує
пул ARQ; його закриває сам ARQ. `enqueue()` підтримує `defer` у секундах або
`timedelta`, іменовані аргументи та `job_id` для уникнення дублікатів.
Повертає ARQ `Job`, або `None`, якщо такий `job_id` уже існує.

Worker виконує шість задач:

- `poll_generation`: читає статус RunPod, оновлює генерацію й планує наступну
  перевірку через `GENERATION_POLL_INTERVAL_SECONDS`. Для завершених задач
  записує `completed_at`, для невдалих — також `error`. Запити до RunPod
  виконуються поза транзакцією БД. Паралельна зміна або скасування генерації
  має пріоритет над застарілою відповіддю polling.
- `recover_generations`: при старті та щохвилини відновлює polling активних
  генерацій із `runpod_job_id`. Повторне відновлення використовує той самий ID
  задачі для поточного `updated_at`. Застарілі задачі пропускаються.
- `reconcile_payments`: при старті та кожні 5 хвилин звіряє останні 7 днів
  транзакцій ATLOS і Telegram Stars. Це страхує від пропущеного postback,
  webhook або повідомлення бота; повторне зарахування ідемпотентне.
- `cleanup_pending_payments`: при старті та щохвилини переводить `PENDING` і
  `PROCESSING` із минулим `expires_at` у `EXPIRED`. Потім видаляє `EXPIRED` і
  `CANCELLED` записи, старші за 30 днів. Захищені записи не видаляються:
  наявність транзакції, повернення, `paid_at`, `paid_amount`,
  `provider_transaction_id`, `asset_amount`, `blockchain_hash` або
  `sender_address` зберігає фінансовий слід. Баланс гаманця не змінюється.
  Рахунки без строку дії не прострочуються.
- `cleanup_generations`: при старті та кожні 10 хвилин видаляє завершені,
  невдалі, скасовані й прострочені генерації, старші за
  `GENERATION_RETENTION_DAYS` (типово 7 днів). Спочатку видаляється файл у
  MinIO; якщо сховище не підтвердило видалення, запис лишається для повторної
  спроби. Пов'язані транзакції зберігаються, а їхній `generation_id` стає
  `NULL`. Активні генерації не зачіпаються.
- `cleanup_generation_images`: при старті та кожні 10 хвилин прибирає об'єкти
  `generations/` у MinIO. Файли, старші за `MINIO_RETENTION_HOURS`, видаляються
  незалежно від наявності запису; файли без запису в БД отримують додатковий
  grace-період `IMAGE_ORPHAN_GRACE_HOURS`. Курсор зберігається в Redis, тому
  перезапуск не починає скан спочатку. Помилка видалення одного об'єкта не
  блокує решту: він буде повторно перевірений після завершення повного кола.

Порядок і параметри очищення задаються в `TaskQueueSettings`; для `.env`
доступні `GENERATION_RETENTION_DAYS`, `GENERATION_CLEANUP_BATCH_SIZE`,
`IMAGE_CLEANUP_BATCH_SIZE` та `IMAGE_ORPHAN_GRACE_HOURS`.

Транзакції використовують наявний `session_scope()`. Наступна перевірка
публікується після commit; якщо публікація не відбулася, її відновить cron.
При тимчасових помилках RunPod, БД або Redis polling повторюється з паузою
через ARQ `Retry`. Вичерпання спроб не робить генерацію невдалою:
наступне відновлення знову перевірить її фактичний стан.

Без `RUNPOD_API_KEY` відстеження генерацій вимкнене, прострочення та
звіряння оплат працює. Worker не надсилає нові генерації. Якщо MinIO
налаштований, worker зберігає зображення перед фіксацією `COMPLETED`.
Збій читання результату, відсутнє inline-зображення або невдалий запис у
MinIO залишає генерацію активною та запускає повторну спробу. Без MinIO
поведінка залишається прямою: статус береться з RunPod, зображення читає API.
Зарахування оплат виконується через reconciliation-сервіс:
він перевіряє підтвердження провайдера, ідемпотентно зараховує кредити й
обробляє пізні оплати навіть для локально прострочених рахунків.

Поведінка повторного виконання та унікальних ID описана в
[документації ARQ](https://arq-docs.helpmanual.io/).
