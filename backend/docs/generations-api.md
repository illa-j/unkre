# Generations API

Маршрути підключені в `main.py` і використовують наявний `GenerationService`.
Авторизація — access JWT у cookie `cl_access_token`. Користувач визначається
із сесії; чужа й відсутня генерація повертають однаковий 404.

| Метод | Шлях | Призначення |
| --- | --- | --- |
| POST | `/generations` | Створити власну генерацію й одразу відправити її в RunPod |
| GET | `/generations` | Власні генерації від нових до старих |
| GET | `/generations/{generation_id}` | Переглянути власну генерацію та її статус |
| GET | `/generations/{generation_id}/image` | Отримати результат завершеної власної генерації |
| DELETE | `/generations/{generation_id}` | Видалити власну генерацію; активну задачу спочатку скасувати |

Для списку доступні `limit` від 1 до 100 (типово 100) та `offset` від 0.
POST і DELETE проходять [CSRF-перевірку](api-guard.md). Відповіді мають
`Cache-Control: no-store`.

## Створення

```json
{
  "workflow_id": "01900000-0000-7000-8000-000000000001",
  "prompt": "A portrait in soft natural light",
  "images": [],
  "loras_strength": {
    "01900000-0000-7000-8000-000000000002": 0.7
  },
  "seed": 42
}
```

Обов'язкові поля — `workflow_id` та `prompt`. Prompt після обрізання пробілів
має містити від 1 до 8192 символів. `images` — список непорожніх base64-рядків
без префікса `data:`. Непорожній `images` дозволений лише для workflow
`Qwen Image 2.1` і містить **до 16** референс-фото: перше стає `input.png`,
решта — `input_2.png` … `input_16.png`, а вузол `TextEncodeQwenImage21`
отримує відповідні `images.image_1..16` (його autogrow-вхід оголошує саме 16
слотів). Більше 16 або референси для інших моделей повертають 422 до
збереження генерації чи запуску RunPod. `seed` — ціле число від 0 до `2**63-1`; якщо пропущений
або `null`, сервіс генерує випадковий seed.

`loras_strength` містить UUID LoRA, доступних у вибраному workflow, та скінченні
числові ваги. Кількість LoRA не обмежена: можна передати будь-яку підмножину
каталогу workflow, кожну зі своєю вагою. Пропущене поле або `null` залишає ваги з
JSON-графа; порожній об'єкт `{}` вимикає LoRA у графі. Імена LoRA й назва JSON
workflow визначаються сервером із БД.

Додаткові поля, зокрема `user_id`, `status`, `credits_spent`,
`runpod_job_id`, `runpod_endpoint_id` та `uploaded_images`, відхиляються.

Відповідь 201 містить `id`, `workflow_id`, `prompt`, `loras_strength`,
`uploaded_images`, `status`, `seed`, `error`, `credits_spent`, `completed_at`
і `created_at`. Після успішного запуску статус — `queued`.
RunPod job ID та endpoint залишаються внутрішніми полями.

Статус надалі оновлює наявний worker; він підхоплює збережений запис після
commit при наступному проході recovery. POST автоматично не повторює запуск
при помилці провайдера. Commit і rollback виконує наявний `session_scope()`.

## Перегляд і видалення

GET одного запису повертає ту саму схему, список — масив записів.
Перегляд працює без налаштованого RunPod і не звертається до його API.

Успішне видалення повертає 204 без тіла. Для активної генерації сервіс
скасовує RunPod job на збереженому endpoint. Якщо скасування не вдалося
або job залишився активним, запис не видаляється. Завершені генерації
видаляються без звернення до RunPod; разом із записом прибирається копія
з тимчасового кешу MinIO. Якщо MinIO не підтвердив видалення файла,
повертається 503, а запис у БД не видаляється, щоб очищення можна було
повторити. Фінансова історія зберігається.

Окремо worker автоматично видаляє завершені, невдалі, скасовані й
прострочені генерації через `GENERATION_RETENTION_DAYS` (типово 7 днів).
Кеш зображень при цьому живе лише `MINIO_RETENTION_HOURS` (типово 24
години); див. [image-cache.md](image-cache.md).

## Результат зображення

`GET /generations/{generation_id}/image` повертає байти результату з
`Content-Type: image/png`, `image/jpeg` або `image/webp` і
`Cache-Control: no-store`. Маршрут доступний лише власнику завершеної
генерації; для активної, чужої або відсутньої генерації повертається 404.
Backend спершу пробує тимчасовий кеш MinIO, а якщо об'єкта немає — бере
збережений `runpod_endpoint_id` і `runpod_job_id` та запитує output у RunPod,
після чого кладе успішну відповідь у кеш. Якщо output відсутній або не є
PNG/JPEG/WebP, повертається 404 або 502. Постійного сховища зображень немає:
кеш живе 24 години (див. [image-cache.md](image-cache.md)), а постійна копія
лишається в браузері користувача.

## Каталог workflow

`GET /workflows?limit=100&offset=0` повертає доступні моделі та сумісні LoRA
з БД. Маршрут потребує авторизованої user cookie. `limit` — від 1 до 100,
`offset` — від 0. Кожен workflow містить `id`, `name`, `description`,
`generation_credits`, `loras` і `recommended_strengths`; кожна LoRA — `id`,
`name`, `description`, `preview_urls`. `recommended_strengths` — мапа
`lora_id → strength`, рекомендована автором саме для цієї моделі (одне й те саме ім'я
файлу може мати різні значення для різних моделей; дані з маніфестів
`scripts/*_manifest.json`, колонка `workflow_loras.recommended_strength`).

`is_active` показує, чи модель доступна в студії. Неактивні workflow
лишаються в базі для історії генерацій, але не повертаються публічним
`GET /workflows` і не приймають нові генерації чи пресети. Зараз у продакшені
активні `krea2_turbo_all_api` і `Qwen Image 2.1`; `krea2_raw_t2image_api`
виведено з обігу. `generation_credits` — ціна однієї генерації в кредитах
(0 — безкоштовно). Фронтенд використовує ці UUID у `POST /generations`,
а не назви моделей.

## Пресети генерацій

`GET /presets?limit=100&offset=0` повертає збережені пресети поточного користувача.
Кожен пресет містить `id`, `name`, `description`, `workflow_id`, `prompt`,
`negative_prompt`, `loras_strength` (UUID → вага), `seed` і часові позначки.

`POST /presets` створює пресет із тими самими полями, що й генерація:

```json
{
  "name": "Soft portrait",
  "description": "Soft window light and natural skin texture.",
  "workflow_id": "01900000-0000-7000-8000-000000000001",
  "prompt": "natural light portrait, realistic skin",
  "negative_prompt": "blurry, text",
  "loras_strength": {
    "01900000-0000-7000-8000-000000000010": 0.7,
    "01900000-0000-7000-8000-000000000011": 0.4
  },
  "seed": 42
}
```

`name` — 1–100 символів, `description` — 0–1000,
`prompt` — 0–8192, `negative_prompt` — 0–8192,
`seed` — 0…2**63-1 або `null`. `loras_strength` може містити будь-яку кількість
LoRA з вибраного workflow.

### Завантаження preview у MinIO

`POST /presets/previews` приймає `multipart/form-data` з полем `file`
(PNG, JPEG або WebP до 10 MB). Файл перевіряється за сигнатурою, зберігається
в MinIO під `preset-previews/<preview_id>` і не потрапляє під 24-годинний
lifecycle генерацій. Відповідь:

```json
{"id": "01900000-0000-7000-8000-000000000020", "url": "/api/presets/previews/01900000-0000-7000-8000-000000000020"}
```

Отриманий `url` передається в `preview_urls` при створенні або оновленні
пресета. `GET /presets/previews/{id}` віддає зображення з довгим immutable
кешем. Для адмінки використовується `POST /admins/presets/previews`; публічний
GET той самий. Старі зовнішні `http(s)` preview URL залишаються сумісними.

`PATCH /presets/{id}` оновлює будь-яку підмножину полів — рівно те, що є в
тілі запиту. Явний `null` очищає `seed` або `loras_strength`, пропущене поле
лишається як було; порожній обʼєкт повертає 422. Якщо змінюється `workflow_id`,
наявні LoRA перевіряються проти нової моделі (невідповідні — 422), а
`loras_strength: null` очищує їх. `DELETE /presets/{id}` видаляє пресет; чужі
пресети невидимі й повертають 404 для всіх трьох методів.

## Помилки

- 401 — відсутня або недійсна user cookie;
- 402 — недостатньо кредитів для генерації;
- 403 — користувач заблокований або не пройдена CSRF-перевірка;
- 404 — генерація не належить користувачу, відсутня генерація чи workflow;
- 409 — RunPod job залишився активним після спроби скасування;
- 422 — некоректні дані, зображення, LoRA або JSON workflow;
- 503 — RunPod не налаштований, недоступний або повернув некоректну відповідь;
  також помилка видалення файлу з MinIO під час `DELETE`.
