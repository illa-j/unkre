# Аудит платежів бекенду — 4 листопада 2026

Перевірено створення рахунків ATLOS і Telegram Stars, автентифікацію вебхуків,
pre-checkout, зарахування кредитів, повторну доставку підтверджень, звірку з
провайдерами, журнал транзакцій, реферальні нарахування та очищення рахунків.

## Виправлені помилки

1. **Частковий commit після помилки Telegram polling.** Обробники перехоплювали
   винятки всередині `session_scope()`. Помилка після покупки, наприклад під час
   реферального бонусу, могла залишити платіж і баланс збереженими без завершення
   всієї операції. Обробка винятків перенесена за межі транзакції. Повідомлення
   про успіх надсилається лише після успішного commit; збій pre-checkout відхиляє
   оплату після rollback.
2. **Один проблемний запис блокував звірку інших платежів.** Невідповідність суми,
   конфлікт транзакції чи помилка валідації реферального бонусу переривали обробку
   всієї вибірки. Кожен запис тепер має savepoint, який охоплює платіж, баланс,
   журнал і бонуси. Некоректний запис відкочується та потрапляє в лог, решта
   продовжують оброблятись. Інфраструктурні помилки не приховуються: вони
   переривають зовнішню транзакцію для повтору наступним запуском worker.
3. **Не зберігався фактичний платник Stars для акаунта без Telegram.**
   Після підтвердженої оплати `telegram_user_id` залишався порожнім, хоча для
   повернення Stars потрібні ID платника й charge ID. Тепер платник фіксується
   з автентифікованої події або відповіді звірки. Дозволено лише одноразове
   заповнення порожнього поля під час успішного зарахування. Заміна вже
   збереженого платника заборонена; повтор створення рахунка з тим самим ключем
   залишається ідемпотентним після такого заповнення.
4. **Формат дат ATLOS Transaction/List.** Публічна документація описує
   `YYYY-MM-DD hh:mm:ss`, але живий API повертає на цей формат `400 Bad
   Request`. Після перевірки залишено ISO-8601 (`datetime.isoformat()`), який
   API приймає; дати попередньо переводяться в UTC.

## Перевірка

- Початковий набір платіжних тестів: 147 успішних.
- Платежі, реферали та worker після змін: 184 успішних.
- Повний набір бекенду після змін: **790 успішних** (`.venv/bin/pytest`).
- Додано 9 регресійних сценаріїв. Усі 9 падають на ізольованій копії початкового
  коду й проходять після виправлень. Оновлено перевірку формату дат ATLOS.
- `ruff check src tests`: без помилок.
- Наявні тести перевіряють підпис ATLOS, секрет Telegram webhook, доступ лише до
  власних платежів, неправильні суми/валюти/платника, повторні підтвердження,
  заборону одного charge ID для двох рахунків і запізніле підтвердження оплати.

## Межі перевірки

Це аудит вихідного коду й локальних тестів. Провайдери замінені mock-відповідями,
БД у платіжних регресійних тестах — тимчасова SQLite. Реальні списання,
виробнича БД, конкурентні блокування PostgreSQL і доставка живих вебхуків
не перевірялися. Зміни не потребують нової міграції; деплой не виконувався.

Повернення коштів представлене моделями зберігання, але окремого сервісу/API
повернення в поточному бекенді немає. Наявний історичний платіж без збереженого
платника цими змінами автоматично не доповнюється; для такого повернення
потрібне відновлення ID платника з історії Telegram.
